# Адаптация SHAD Tutoring под личный стек

Дата: 24 ноября 2026, Asia/Irkutsk. Исходный снимок: локальный коммит `4e4d62c`.
Исходный проект уже вызывал fastbase → core-package → event-infra → PostgreSQL.
Адаптация доводит эту реализацию до текущих правил стека и воспроизводимого запуска.
Vue 3 / Vite / Pinia, страницы, оформление, предметные правила и API сохранены.

## Границы и архитектура

- Внешний сценарий: HTTP-маршрут с явной моделью ответа и
  `@external_scenario(action, core=...)`; DTO формируется транспортом.
- Доступ: `app/api/access.py`, единственный конфиг `config/access.toml`.
  Ровно одна роль из проверенного access JWT; body не назначает principal.
  Неизвестное действие/роль и отсутствие разрешения закрывают доступ до core.
- Внутренний сценарий: `BaseScenario.execute(dto)`, вызов `run()`,
  зарегистрированные DTO/response, SQL через `self._db` и нужный канал.
  Повторные ролевые ACL админских внутренних сценариев удалены; предметное
  владение конфигурациями, уроками и участниками по-прежнему проверяет core.
- Предметные модули сохранены в существующих группах `app/scenarios/`:
  учётные записи, профили, связи, доступность, уроки/участники, уведомления,
  статистика и журнал. Модели и прежние имена таблиц остаются в `models.py`.
- Фоновый frontend-журнал отправляется только при наличии access-токена.
  Его 401 не вызывает refresh или сброс пользовательской сессии; гостевые
  переходы не создают повторяющиеся запросы к закрытому журналу.
- Запись журнала перенесена из HTTP-обработчика в core-сценарий
  `system_write_logs`; формат и файловое хранение журнала сохранены.
- Один lifecycle на процесс: event-infra → core → проверка регистрации →
  роли → HTTP; при остановке core → EventRouter, включая ошибку старта core.
  Один worker закреплён из-за существующих блокировок расписания и сессий.
- Старт приложения не генерирует и не применяет миграции.
  Только read-only проверка схемы/ревизии. Команда применения —
  `python -m scripts.migrate`, код миграций хранится в Git.
- Кеш event-infra выключен, потому что текущие SQL-мутации не обеспечивают
  его инвалидацию. Это сохраняет актуальность результата после записи.

## Контракты и совместимость

Снимок исходной поверхности — `tests/fixtures/api_surface.json`:
**65 HTTP-действий**, включая health. Все исходные методы/пути сохранены;
новый `/api/v1/ready` доводит число до 66. Всего 65 внутренних сценариев.
Проверка сопоставляет исходные действия с текущими маршрутами и response-моделями.
Сквозной тест требует успешного выполнения каждого исходного действия.
Тесты отказов проходят по всем запрещённым парам «роль → HTTP-действие».

Существенные уточнения:

- При отсутствии Authorization защищённый запрос получает **401** вместо
  прежней ошибки обязательного заголовка 422. Невалидный токен не превращается
  в guest. Предметные коды/ответы, включая 422 для отозванного refresh, сохранены.
- Входные даты со смещением по-прежнему преобразуются в локальное серверное
  время. Хранение и выходные строки дат согласованы с `docs/time-rules.md`:
  локальное время без offset. Ранее SQLModel 0.0.48 выбирал UTCDateTime при
  аннотации datetime, а прикладная логика передавала naive datetime.
- В `models.py` явно указан `NaiveDatetime`; JSON-поля допускают прежний
  закодированный вид event-infra и Python-объекты. Колонки JSON, структура,
  идентификаторы и чтение старых значений через кодек сохраняются.
- `run_infrastructure.py --test` сохранён как запуск защищённой проектной
  регрессии перед инфраструктурой. Удаление пакетных тестовых таблиц заменено
  изоляцией собственных тестовых записей и временных БД.

## Переход данных

Сохранена исходная ревизия `35a2d259c8b6`; добавлена
`20261124_server_time`. Она переводит только timezone-столбцы дат в timestamp
без зоны через `AT TIME ZONE current_setting('TIMEZONE')`. Уже подходящие
столбцы не изменяются. Поэтому проверяются и поддерживаемая naive-схема, и исходная timestamptz-схема.

На локальной БД подтверждён часовой пояс **Asia/Irkutsk**. До преобразования
рабочих записей создана отдельная временная БД: перенесены все 12 прикладных
таблиц с исходными ID/FK/JSON, применена миграция, сравнены канонические хеши
всех строк с нормализованными серверными датами. После совпадения тот же
переход применён к рабочей БД. Все строки, связи, JSON и локальные значения
дат совпали; ревизия и фактическая схема проверены. Временная копия удалена.
Рабочие пароли, JWT-секрет и подключения сохранены.

На другой существующей БД перед применением требуется проверить её исходный
часовой пояс: перевод должен сохранять время именно исходного сервера.
Чистая установка проходит обе миграции подряд; отдельные тесты проверяют
пустую схему, заполненную схему, связи и повторное применение.
