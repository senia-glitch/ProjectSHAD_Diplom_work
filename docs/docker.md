# Запуск SHAD Tutoring в Docker

## Одна команда

Нужен запущенный Docker Desktop в режиме **Linux containers** с Docker Compose v2.
Python, Node.js и PostgreSQL на Windows для этого режима не требуются.

Из корня проекта:

```powershell
.\dev.ps1
```

Команда по умолчанию — `up`. Первый запуск создаёт отсутствующий `.env`
со случайным паролем PostgreSQL и JWT-секретом, собирает образы, запускает
PostgreSQL, применяет проверенные миграции отдельным процессом и поднимает
backend и frontend. Скрипт ждёт healthchecks и проверяет страницу и готовность
HTTP → core → PostgreSQL через frontend-прокси.

| Компонент | Адрес по умолчанию |
|---|---|
| Приложение | http://localhost:3000 |
| Swagger UI через сайт | http://localhost:3000/docs |
| API напрямую | http://localhost:18080/api/v1 |
| PostgreSQL | 127.0.0.1:15432 |

Порт 18080 выбран, поскольку 8000 занят другим локальным контейнером.
Порты задаются в `.env`; все публикации привязаны к localhost.

Если локальная политика PowerShell блокирует `.ps1`, можно выполнить скрипт
с настройкой только для текущего процесса:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\dev.ps1 up
```

## Повседневные команды

```powershell
.\dev.ps1 up          # собрать изменившееся и дождаться готовности
.\dev.ps1 down        # остановить и удалить контейнеры, сохранив данные
.\dev.ps1 stop        # только остановить контейнеры
.\dev.ps1 restart     # пересобрать изменённый код и снова запустить
.\dev.ps1 logs        # backend и frontend; Ctrl+C завершает просмотр
.\dev.ps1 logs db migrate
.\dev.ps1 ps
.\dev.ps1 test        # оба набора тестов в контейнерах
.\dev.ps1 test -k security  # фильтр backend-тестов; затем все frontend-тесты
.\dev.ps1 psql
.\dev.ps1 shell
.\dev.ps1 migrate     # отдельно применить уже написанные миграции
.\dev.ps1 build       # только собрать runtime-образы
.\dev.ps1 check       # проверить Compose без запуска Engine
.\dev.ps1 help
```

Скрипт использует путь к своей папке: его можно вызывать из другой рабочей
директории, и после выполнения текущая директория восстанавливается.
Любая неуспешная команда Docker возвращает ненулевой код; сбой тестов не
скрывается последующими командами. Готовность не объявляется после ошибки запуска.

`restart` собирает код из текущей рабочей копии. Автоматические bind-mount
и autoreload не используются; содержимое образов соответствует результату сборки.

## Данные и настройки

По выбранному варианту Docker начинает с **пустой собственной БД**.
Роли и таблицы создаются приложением и миграциями; аккаунт можно зарегистрировать
через интерфейс. Демо-пользователи и администратор автоматически не добавляются.

Compose-проект называется `shad-tutoring`. Его тома:

- `shad-tutoring_pgdata` — PostgreSQL, включая основную и тестовую БД;
- `shad-tutoring_app-logs` — файловый журнал приложения.

Имена меняются вместе с `COMPOSE_PROJECT_NAME`. `down`, `stop`, `restart`
и повторный `up` сохраняют тома. Команд удаления томов в `dev.ps1` нет.

`.env` нужен для повторного подключения к тому же PostgreSQL и проверки JWT.
Существующий файл никогда не перегенерируется. Локальные `.infra.env`,
`.core-package.env`, `.env.fastbase` обычного запуска не меняются.
В Docker используются отдельные настройки из `docker/infra.env`, безопасного
HTTP-шаблона и переменных Compose. `.env` исключён из Git и контекста сборки.

```powershell
.\dev.ps1 init
.\dev.ps1 up -EnvFile .env
```

При указании другого `-EnvFile` путь относительно корня проекта. В файле
поддерживаются простые значения и значения в кавычках; переменные процесса
имеют приоритет, как в Compose. Генерируемые секреты содержат только hex-символы,
чтобы пароль корректно помещался в URL PostgreSQL.

Backend и PostgreSQL работают в UTC (`TZ=UTC`, `timezone=UTC`): сервер хранит и считает
время только в UTC, личный часовой пояс — настройка пользователя (показ). `SHAD_TIMEZONE` —
пояс, в котором были записаны данные до перехода на UTC; его один раз читает миграция
`20261125_utc_scheduling` (через `SHAD_LEGACY_TIMEZONE`). Для новой пустой базы значение не важно.

## Состав контейнеров

| Сервис | Назначение |
|---|---|
| `db` | PostgreSQL 17, постоянный том, readiness через pg_isready |
| `migrate` | runtime-образ backend, команда `python -m scripts.migrate`, завершение с кодом 0 до старта app |
| `app` | Python 3.14, текущие закреплённые пакеты стека, один worker, readiness с настоящим SQL |
| `web` | собранный Vue, unprivileged Nginx на 8080, SPA fallback, прокси `/api/` и документации |
| `api-tests` | профиль `test`, dev-образ backend с pytest/httpx |
| `frontend-tests` | профиль `test`, Node.js 24 и Vitest |

Зависимости backend ограничиваются существующим `requirements.lock`:
`requirements.txt` задаёт runtime, `requirements-dev.txt` добавляет только
dev-инструменты. Git используется в builder, runtime работает от `app` без git
и pytest. Frontend собирается через `npm ci` по существующему package-lock.
Nginx также работает от обычного пользователя. Корневая файловая система
runtime-контейнеров read-only; запись разрешена в `/tmp` и том журнала.

Основной и тестовый URL всегда различаются. `POSTGRES_TEST_DB` создаётся при
первой инициализации тома; `dev.ps1 test` также безопасно создаёт отсутствующую
тестовую БД в существующем томе без сброса данных. Backend-тесты создают
собственные записи и временные БД; frontend-тесты не подключаются к PostgreSQL.

Образы и секреты не публикуются. Обычный запуск Compose без PowerShell:

```powershell
docker compose --env-file .env -f docker-compose.yml up -d --build --wait
```

Порядок старта опирается на [условия зависимостей Compose](https://docs.docker.com/compose/how-tos/startup-order/):
готовая БД → успешный migrate → готовый backend → frontend.
`--wait` ожидает [готовности сервисов](https://docs.docker.com/reference/cli/docker/compose/up/).

## Проверки скрипта

В разработке Windows-ветви `dev.ps1` проверяются отдельно без реального Docker:

```powershell
.\venv\Scripts\python.exe -m scripts.test_dev
```

Проверяются ожидание готовности, сохранение секретов, ненулевой код при сбое,
изоляция тестовой БД, передача pytest-аргументов и остановка без удаления томов.
Это дополнение к реальной сборке, контейнерным тестам и проверке сохранности
данных между `down` и `up`.

## Результат проверки 24 ноября 2026

На Docker Desktop с Linux Engine выполнены настоящая сборка и запуск через
`dev.ps1`: `db`, `app`, `web` стали healthy, `migrate` завершился с кодом 0.
В контейнерах прошли **207 backend-тестов** и **187 frontend-тестов**,
отдельно в Windows PowerShell 5.1 — **9 проверок скрипта**.

Через браузер проверены регистрация, изменение профиля и сохранение после
перезагрузки. После `down` → `up` значения и количество строк во всех 12
прикладных таблицах совпали; контейнерные тесты также не изменили основную БД.
Локальный `.env` сохранился побайтно. Подтверждены непривилегированный runtime,
отсутствие git/pytest и локальных файлов с секретами в backend-образе.

Проверены SPA-маршруты, готовность API через Nginx, документация API и часовой
пояс UTC+8. Созданный для проверки аккаунт удалён через API: основная Docker-БД
оставлена без пользователей и занятий, с тремя служебными ролями.
