## 1. Инфраструктурный стек

### 1.1 Цель стека

Стек — самодельная связка из трёх независимых пакетов (создаются генераторами `fb init`, `infra-init`, `core-init`). Цель конструкции:

1. **Минимум магии.** Каждый слой понимается по одному файлу документации, всё управляется env-переменными, запуск — одна команда.
2. **Жёсткие границы слоёв.** Транспорт не знает о бизнес-логике, бизнес-логика не знает об HTTP и БД-драйверах.
3. **Переносимость.** Любой пакет можно выкинуть и заменить голым аналогом (escape hatch: `fastbase` → обычный FastAPI, `core-package` → свои классы, `event-infra` → любой async-доступ к БД через абстракции).
4. **Скорость старта и развития.** Добавление модели/сценария/роута = добавление файла + перезапуск. Ручных регистраций нет.

### 1.2 Состав

| Пакет | Роль | Конфиг | Ключевые вещи |
|---|---|---|---|
| **fastbase** | HTTP-транспорт поверх FastAPI | `.env.fastbase` (`FAT_*`) | `make_app()`, `start()`, авто-сборка роутеров, единый конверт ошибок, `X-Request-ID` и access-log middleware |
| **core-package** | Ядро бизнес-логики | `.core-package.env` (опционален) | `BaseScenario`, реестр сценариев, `run("имя", dto)`, DI (`IDatabase`, `ICache`, `ILogger`, `IMetrics`), JWT/bcrypt/утилиты дат и валидации |
| **event-infra** | Доступ к PostgreSQL | `.infra.env` | Пулы соединений и очереди по каналам, универсальный CRUD (`create/read/update/delete/custom`), авто-миграции Alembic по `models.py` |

Поток запроса:

```
HTTP-запрос
  → fastbase (роут, middleware, конверт ошибок)
  → run("scenario", dto)          [core-package]
  → сценарий: self._db.create/...  [EventInfraDatabaseAdapter]
  → event-infra (EventRouter: канал → очередь → пул)
  → PostgreSQL
```

### 1.3 Конфигурация

Три файла, каждый отвечает за свой слой:

- `.env.fastbase` — заголовок OpenAPI, префикс `/api/v1`, пакет роутов, интеграции (`FAT_INTEGRATIONS=core,event-infra`), дискавери сценариев (`FAT_CORE_DISCOVER=app.scenarios`), хост/порт uvicorn, уровни логов, маппинг числовых кодов ошибок (`FAT_ERROR_CODES`).
- `.infra.env` — `DB_URL` (синхронный, для миграций) и `DB_URL_ASYNC` (asyncpg, для работы), список каналов, размеры пулов и очередей по каждому каналу, retry, кеш чтения, логирование.
- `.core-package.env` — секрет и времена жизни JWT, раунды bcrypt, метрики, логи. Может отсутствовать, если всё задано в `.env.fastbase`.

### 1.4 Правила и паттерны бэкенда

**Модель данных.**
- `models.py` в корне — единственный источник истины о схеме БД. Миграции (Alembic) генерируются автоматически при старте приложения: сравнение `models.py` с реальной БД, при отличии создаётся ревизия.
- Изменить схему = отредактировать `models.py` + перезапустить. Ручные `alembic revision` не нужны.

**Авто-сборка.**
- Роуты: пакет `app.api.v1.routes` сканируется; модуль участвует, если экспортирует `router: APIRouter` (необязательный `prefix` добавляется к `FAT_API_PREFIX`). Модули с `_` и без `router` пропускаются, ошибка импорта модуля — warning без падения.
- Сценарии: пакет `app.scenarios` обходится при старте; сценарий регистрируется декоратором `@register_scenario("имя")` + `@tracked_scenario("имя")` (трекинг в метриках).

**Паттерн сценария.**
- Сценарий — класс-наследник `BaseScenario` с методом `execute(dto)`. Вход — pydantic-DTO, выход — pydantic-модель. Сценарий не знает про HTTP, роли и каналы БД.
- Идентичность вызывающего извлекается из access-токена (`extract_token_info(dto.access_token)`); токен в DTO прокидывает роут.
- Чистая бизнес-логика (без IO) выносится в `app/utils/*` и тестируется отдельно.

**Паттерн роута.**
- Роут — только транспорт: собрать DTO из запроса и вернуть `await run("имя", dto)`.
- Доступ: зависимость `get_current_user` (Bearer-токен, роль из payload) + декоратор `@require_auth(roles...)` на эндпойнте.

**Дисциплина доступа к БД.**
- Каналы: `read`, `write`, `admin` — отдельные пулы и FIFO-очереди; смысл — изолировать тяжёлые запросы от транзакционных.
- `_db.query(...)` по умолчанию идёт в read-канал. Мутации — только через `_db.create/update/delete` или `query(..., channel="write")`.
- Каждая SQL-операция — своя транзакция. **Многошаговые операции неатомарны**: применяется best-effort компенсация (удаление сироты при частичном сбое), а не настоящие транзакции. Паттерн зафиксирован в коде (например, откат урока при неудачном создании участника, откат пользователя при неудачном создании профиля).
- Гонки: проверка пересечений уроков/броней — check-then-insert без блокировки; остаточная гонка двойного бронирования принята как допустимый риск. Гонки на уникальных ключах (участие, пользователь) разруливаются constraint'ом БД + повторным чтением с идемпотентным ответом.

**JSON-поля.**
- Все JSON-колонки (`tutor_settings.self_booking_whitelist/default_links`, `configurations.default_links`, `bookings.access_targets/booking_metadata`, `lessons.lesson_settings/lesson_links/lesson_metadata`, `lesson_participants.participant_settings/participant_metadata`) проходят через единый кодек `app/utils/json_codec.py`: `serialize_for_db` перед любой записью, `parse_row/parse_rows` сразу после чтения, `parse_int_list` перед проверками вхождения.
- Семантика: `None` = «не задано», `[]`/`{}` = «пусто, но задано».

**Время.**
- Серверное время — единственно верное: хранение, вычисления, проверки. Клиент работает в своей таймзоне, преобразование — на границе API.
- Формат ISO 8601, интервалы полуоткрытые `[start, end)`, максимум длительности записи/брони — 168 часов (1 неделя).
- Aware-вход конвертируется в серверное локальное время (не отбрасывает смещение).

**Ошибки.**
- Единый конверт: `{"success": false, "error": {"code": ..., "message": ..., "details": ...}}` — доменные исключения, `HTTPException`, ошибки валидации и необработанные исключения приводятся к нему.
- Иерархия `fastbase.errors`: `NotFoundError` (404), `ValidationError` (422), `ConflictError` (409), `UnauthorizedError` (401), `ForbiddenError` (403), `InternalError` (500). Числовые коды — через `FAT_ERROR_CODES`.
- Требуется `FAT_INTEGRATIONS=core,event-infra`, иначе ошибки ядра уйдут как 500.

**Аутентификация.**
- JWT: access ~15 минут, refresh ~30 дней (настраивается), bcrypt 12 раундов, пароль 8–72 байта (лимит bcrypt).
- Роль (`student`/`tutor`/`admin`) живёт в токене; открытая регистрация — только student/tutor, админ создаётся служебно.
- Refresh-токен хранится в `users.refresh_token` (открытым текстом — см. 4.5).

**Лимиты выборок.**
- Год уроков: `LIMIT 5000` (статистика), детализация за период ≤ 366 дней и `LIMIT 5000`, прогноз «вперёд» — `LIMIT 500`. Назначение — защита от сверхвыборки.
- Пагинация — `LIMIT/OFFSET` в SQL. Исключение — `student_get_my_lessons` (строит список по участиям с фильтрами в Python) — известный техдолг.

### 1.5 Запреты бэкенда

- Бизнес-логика в роутах; HTTP-понятия (статусы, заголовки) в сценариях.
- `json.dumps/loads` в сценариях мимо кодека; deprecated `serialize_json_fields` для нового кода.
- Мутации через `_db.query(...)` без явного `channel="write"`.
- `datetime.fromisoformat` напрямую в сценариях — только `app/utils/safe_parse.py` (даёт `ValidationError`, а не 500).
- Пагинация срезом Python для списков, отображающихся 1:1 на таблицу.
- CORS/GZip/TrustedHost fastbase не ставит — добавляются вручную при необходимости.
- Свои числовые коды ошибок — только через `FAT_ERROR_CODES`, не в коде.

### 1.6 Возможности стека

- Автоматические миграции и CRUD любой сущности из `models.py` без написания SQL.
- Произвольный SQL через `custom/query` с выбором канала.
- Добавление каналов БД под нагрузку (например, `report`) одной строкой в `.infra.env`.
- Метрики сценариев (`tracked_scenario`), метрики пулов/очередей (`infra-monitor`, `/system/stats`).
- Лог фронтенда в бэкенд (`POST /logs`) и его просмотр в админке — телеметрия UI.
- Кеш чтения, retry соединений, request-id сквозная трассировка (заголовок `X-Request-ID` логов и ответа).

### 1.7 Границы стека (что стек НЕ делает)

- Только PostgreSQL (asyncpg). Одна БД на процесс. Очереди FIFO, без приоритетов.
- Нет своего ORM-движка поверх — вся работа с БД через `IDatabase` (сырые строки dict).
- Нет настоящих многошаговых транзакций — только компенсации.
- Нет фоновой шедулинговой подсистемы (планировщика задач) — событийные уведомления только в момент действия. `notification_lead_time_hours` хранится, но напоминания по времени не отправляются.
- Нет эквайринга/платёжных провайдеров, нет почты/Telegram, нет SSO, нет файлов (только ссылки).
- `/system/*` и `POST /logs` открыты без аутентификации — только для разработки; перед публичным деплоем закрыть ролью `admin` и убрать приём логов.
- Rate limiting на login/register отсутствует.

### 1.8 Фронтенд: архитектура

Стек: Vue 3 + Vite + Pinia + Vue Router. Полные правила — `docs/frontend-rules.md`, дизайн — `frontend/правила и паттерны frontend/паттерны UI.md`. Выжимка:

- Две ветки: `logic/` (api, actions, store, utils, constants) и `ui/` (App, app/router, pages, blocks, composables, components, styles). Зависимость строго **`ui → logic`**, обратная запрещена.
- Контракты: каждая папка-модуль имеет `index.js`; снаружи — импорт только через контракт.
- `api/` — один эндпойнт = одна функция, маппинг ответа в доменную форму; `actions/` — один пользовательский сценарий = одна функция, интерпретация результата и запись в store. Store — без сети; ошибки не пишутся в store.
- Аутентификация: токены в `sessionStorage` (осознанно, не cookie), refresh single-flight (параллельные 401 делят один запрос), провал refresh очищает сессию без сетевых вызовов, guard восстанавливает сессию до проверки доступа, logout сбрасывает все доменные store (seq-guard инвалидирует in-flight загрузки).
- Серверные ссылки перед рендером — через `safeUrl` (только `http(s)`).
- UI-кит (`ui/components`) — компоненты, использованные в 3+ местах; не знает о бизнесе. Блоки (`ui/pages/<page>/`) — составные части страницы.
- Тесты рядом с кодом (vitest), тесты `logic/` не зависят от Vue/DOM.
- Запреты: сетевые вызовы вне `api/`, обращение к API из `ui/`, запись store вне `actions/`, доменная логика в `ui/`, импорты мимо `index.js`, разрыв `.vue` на отдельные файлы разметки/логики/стилей.

### 1.9 Дизайн-система

- Источник правды по значениям — `ui/styles/tokens.css` (палитра, шрифт Segoe UI, отступы, скругления, тени) и `base.css` (кнопки, модалки, формы, примитивы строк). Hex-цвета в компонентах запрещены.
- Каркас страниц: заголовок + три колонки (информация 240px / сетка flex / создание 384px), контент `max-width: 1400px`, шапка на всю ширину.
- Сетка недели: 7 колонок, ячейка 1 час (25px), видимый диапазон 07:00–22:00, время проецируется пропорционально (не рендж 09:15 «на границе часа», а 1/4 ячейки).
- Лестница z-index блоков 5/10/15/20/25 — менять молча нельзя; значки `icon-btn` — только `+`, `−`, корзина.
- Цвета правил доступа (брони): EVERYONE — зелёный, ONLY — жёлтый, ALL_EXCEPT — оранжевый, NOBODY — красный; фон раскрашивает и легенду, и фоновые брони на сетке расписания.
- Туры-подсказки: общий движок `TourOverlay.vue`, шаги задаёт страница; кнопка `?` в заголовке.
- Страницы-реестры (оплаты, журнал): фильтры + метрики-карточки + таблица + пагинация — единый каркас.

### 1.10 Тесты, запуск, диагностика

- Бэкенд: `pytest` (`tests/` — 18 файлов: статусы уроков, пересечения, снапшоты цен, отмены участия, JSON-кодек, приватность ссылок и т.д.).
- Фронтенд: `npm run test` (vitest, тесты рядом с кодом в `logic/` и `ui/pages`).
- Запуск: `python -m app.main` (поднимает миграции → ядро → uvicorn), фронт — `npm run dev`.
- Диагностика: `fb check`, `infra validate`, `infra-monitor`, smoke-скрипты `scripts/smoke/` (`smoke_all.py`, `verify_grid.py`).

## 2. Идея проекта

### 2.1 Описание

**SHAD Tutoring** — платформа для организации занятий с репетиторами. Репетитор — владелец своего времени: задаёт, когда доступен, по каким правилам, по каким ценам. Ученики привязываются к репетитору, видят доступное время и (при разрешении) сами записываются на занятия. Платформа ведёт учёт: расписание, оплаты, уведомления, статистика.

Проект растёт из боли одиночного репетитора: расписание живёт в голове/тетради, записи и переносы — в переписке, оплаты — «по памяти», статистика — в Excel. Каждая из этих задач по отдельности решается простым инструментом, но вместе они отнимают часы и порождают ошибки (двойные записи, забытые оплаты, потерянные ученики).

### 2.2 Цель

**Заменить разрозненные инструменты (тетрадь, Excel, мессенджер, счёт в голове) одним**, который:
- экономит время репетитора на рутине (записи, напоминания, отметки оплат, сводки);
- даёт ученику прозрачность и автономность (расписание, самозапись, материалы, свой прогресс);
- даёт данные для решений (выручка, занятость, потери от отмен, прогноз).

### 2.3 Ключевые концепции (словарь)

| Термин | Смысл |
|---|---|
| **Ресурс** | То, что имеет время и может быть занято. В проекте — репетитор |
| **Владелец ресурса** | Репетитор: распоряжается временем, настраивает доступность, видит записи |
| **Участник** | Ученик: может быть записан к ресурсу |
| **Связь (конфигурация)** | Устойчивое отношение ученик–репетитор с коммерческими и дисциплинарными правилами |
| **Бронь** | Повторяющееся (еженедельное) правило доступа к времени. **Первична**: задаёт рамки |
| **Запись (урок)** | Фактическая фиксация времени на конкретную дату. **Вторична**: заполняет рамки |
| **Правило доступа** | Кто может занять слот брони: все / только перечисленные / все кроме / никто |
| **Слот** | Вычисляемое понятие: интервал, свободный с учётом броней, уроков и правил |
| **Снапшот цены** | Замороженная ставка дня урока в строке участия; смена тарифа историю не трогает |

### 2.4 Роли

- **Гость** — регистрация (ученик/репетитор), вход, выход.
- **Ученик** — связи с репетиторами, расписание, самозапись, уведомления, настройки.
- **Репетитор** — главный персонаж продукта: ученики, расписание доступности, уроки, оплаты, статистика.
- **Администратор** — управление пользователями, системные метрики, журнал фронтенда.

### 2.5 Что уже есть (функциональная сводка)

- Регистрация/вход/профили; персональный номер (`IND-XXXXXXXX`) как способ связи сторон.
- Связи ученик–репетитор с полным набором коммерческих и дисциплинарных настроек.
- Еженедельное расписание доступности (брони) с правилами доступа и цветовой маркировкой.
- Уроки: ручное и самостоятельное создание, групповые/индивидуальные, жизненный цикл по времени, переносы и отмены с уведомлениями.
- Самозапись учеников: расчёт свободных слотов, lead time, белый список.
- Оплаты: отметка оплачено/не оплачено на строке участия, реестр с долгами и сводкой.
- Уведомления внутри приложения (10 типов событий) с непрочитанными.
- Статистика репетитора: выручка/часы/прогноз/отмены/неявки/потери, разрезы по ученикам, дням недели, часам, занятость %, прогноз на 28 дней, CSV-выгрузка по ученикам.
- Календарь (месяц/список), страница урока, туры-подсказки на ключевых страницах.
- Админка: пользователи, списки по ролям, метрики системы, журнал фронтенда.

### 2.6 Чем проект НЕ является (границы предметной области)

- **Не маркетплейс**: нет публичного каталога репетиторов и поиска по базе (поиск ученика/репетитора — только по персональному номеру или ID).
- **Не платёжная система**: деньги двигаются вне платформы; здесь только учёт фактов и отметки.
- **Не LMS**: нет курсов, учебных программ, материалов и ДЗ как сущностей (материалы — пока только ссылки).
- **Не мессенджер**: обмен текстами ученик–репетитор отсутствует.

Эти границы — осознанные: они удерживают проект в рамках «органайзер + учёт». Выход за них возможен, но только осознанно (см. раздел 4).

### 2.7 Ценностная модель

- **Репетитор (основной персонаж, платит временем и деньгами за инструмент):** меньше ручных записей и напоминаний, меньше потерянных оплат, наглядная статистика и прогноз, дисциплина отмен через дедлайны.
- **Ученик:** прозрачное расписание, запись без переписки, материалы урока под рукой, уведомления, свой прогресс.
- **Админ/платформа:** контроль пользователей, телеметрия, здоровье системы.

## 3. Бизнес-правила (по доменам)

Раздел описывает функциональные правила «как для пользователя». Технические детали — в разделах 1 и `docs/`.

### 3.1 Пользователи и доступ

1. Открытая регистрация возможна только в роли ученика или репетитора. Администратора нельзя создать самостоятельной регистрацией.
2. При регистрации выдаётся персональный номер формата `IND-XXXXXXXX` — он уникален и служит «служебным» способом связи сторон (аналог табельного номера).
3. Логин и email уникальны. Логин — латиница/цифры/`_.-`, от 3 символов. Пароль — от 8 символов.
4. Пользователь может посмотреть/отредактировать свой профиль (имя, email, пол, доп. информация) и сменить пароль.
5. Удаление аккаунта удаляет пользователя вместе со связанными данными.
6. Вход выдаёт пару токенов; выход отзывает refresh-токен. Сессия может быть восстановлена при повторном открытии сайта, пока действует refresh-токен.
7. Уведомления доступны любому авторизованному: список с пагинацией, счётчик непрочитанных, «прочитать одно/все».

### 3.2 Связь ученик–репетитор (конфигурация)

1. Между одним учеником и одним репетитором может существовать максимум одна связь (дубль запрещён).
2. Связь создаётся в обе стороны: ученик добавляет репетитора, репетитор — ученика; по ID пользователя или по персональному номеру. Нельзя связать пользователя самого с собой.
3. Новая связь наследует дефолты репетитора: ставку, скидку, дедлайны записи/отмены, ссылки, режим самозаписи (режим YES — самозапись открыта; иначе решает белый список).
4. Параметры связи (правит репетитор):
   - ставка (₽/час) и скидка (%) — коммерческие условия конкретного ученика;
   - шаг записи (мин) — квант самозаписи;
   - самозапись разрешена/запрещена (пер-ученический флаг, согласуется с белым списком);
   - запись возможна не позже чем за N часов до урока; отмена возможна не позже чем за N часов;
   - уведомления включены/выключены и «за N часов»;
   - неоплаченные уроки разрешены/запрещены;
   - видимость ссылок урока: всегда видны / открываются за N минут до урока (0–15);
   - заметки об ученике — видит только репетитор, ученику не отдаются.
5. Конфигурацию можно сбросить к дефолтам репетитора.
6. Удаление связи уведомляет вторую сторону («привязался»/«отвязался»).
7. Коммерческая связь необязательна для существования расписания, но обязательна для добавления ученика в урок и самозаписи.

### 3.3 Профиль и настройки репетитора

1. Статус работы: `WORKING` / `SICK` / `VACATION`. Только `WORKING` позволяет ученикам смотреть слоты и записываться.
2. Ставка и скидка в настройках — глобальные дефолты; фактические цены живут в связях и снапшотах.
3. Режим самозаписи: `YES` — открыта всем связанным; `NO` — только ученикам из белого списка.
4. Дефолтные дедлайны: записи за N часов, отмены за N часов, умолчание — 24 часа.
5. Вид расписания: `INFORMATIVE` / `MINIMALISTIC`, окно отображения (только визуальный диапазон сетки, не право на запись).
6. Дефолтные ссылки (валидируются как `http(s)`) подставляются в создаваемые уроки, если не заданы иные.

### 3.4 Профиль и настройки ученика

1. Статус: `ACTIVE` / `INACTIVE`. Неактивный ученик не может смотреть слоты и записываться.
2. Свои: таймзона (офсет −12…+14), вид расписания (`INFORMATIVE`/`MINIMALISTIC`), окно отображения.

### 3.5 Расписание доступности (брони)

1. Бронь — повторяющееся еженедельное правило: день недели + интервал времени (время хранится без даты).
2. **По умолчанию всё время репетитора недоступно. Бронь открывает время, а не закрывает.**
3. Правила доступа: `EVERYONE` (всем), `ONLY` (только перечисленным), `ALL_EXCEPT` (всем кроме перечисленных), `NOBODY` (никому). Для `ONLY`/`ALL_EXCEPT` список целей обязателен и валидируется: в него входят только ученики со связями с этим репетитором.
4. Брони одного репетитора не должны пересекаться (стык «конец-в-конец» разрешён).
5. Максимальная длительность брони — 168 часов (практически — в пределах суток из-за формата день недели + время).
6. Правило доступа работает одинаково и на своей сетке (цвет блока), и при расчёте слотов для самозаписи.
7. `display_time_*` — только визуальный диапазон сетки и никак не влияет на право записи: в «закрытом» окне записи слоты все равно недоступны, в «открытом» — не открываются.

### 3.6 Уроки

1. Статусы: `SCHEDULED` → `ONGOING` → `FINISHED` двигаются автоматически по серверному времени; `CANCELLED` и `NO_SHOW` ставит репетитор вручную.
2. Терминальные статусы (`FINISHED`, `CANCELLED`, `NO_SHOW`) не меняются временем; время терминального урока править нельзя; вступать/менять участие в терминальном нельзя.
3. Создание урока: нельзя в прошлом, длительность ≤ 168 часов, уроки репетитора не пересекаются (стык разрешён, отменённые уроки не считаются).
4. Урок бывает индивидуальным или групповым (`is_group`).
5. Урок содержит описание, набор ссылок (только валидные `http(s)`), произвольные настройки и метаданные (JSON).
6. Ссылки по умолчанию: при создании учеником — из его связи; при создании репетитором — из настроек репетитора.
7. Перенос урока (правка времени) проверяет пересечения по эффективному интервалу и уведомляет участников.
8. Отмена урока репетитором помечает все активные участия как отмену «репетитором»; уже вышедшие ученики не перезаписываются.
9. Удаление урока удаляет всех участников (жёстко, история строки участия не сохраняется).
10. Репетитор управляет только своими уроками.

### 3.7 Участие в уроках

1. Репетитор добавляет ученика в свой урок; требуется действующая связь. Участие уже отменённое — «возврат»: отмена гасится, снапшот цены и отметка оплаты сохраняются.
2. При добавлении участия фиксируется **снапшот цены** (ставка, скидка, итог за час, валюта, время). Дальнейшая смена тарифа в связи историю не меняет — выручка считается по замороженной цене. Если снапшота нет, цена берётся текущая и помечается как «оценочная».
3. Снятие ученика репетитором и выход ученика помечают отмену (с инициатором и временем), а не удаляют строку — история нужна статистике.
4. Повторные действия идемпотентны: повторный выход/возврат не ломают состояние.
5. Отметка оплаты («оплачено/не оплачено») — на строке участия; оплату отменённой записи менять нельзя; ученик получает уведомление при смене.
6. Ученик видит список только своих уроков; уроки репетитора видны ему только при наличии связи; ссылки урока скрыты, пока он не участник; заметки репетитора недоступны.

### 3.8 Самозапись ученика

1. Самозапись возможна при одновременных условиях: есть связь, флаг самозаписи в связи включён, режим самозаписи репетитора пропускает ученика (YES или whitelist), ученик `ACTIVE`, репетитор `WORKING`.
2. Доступные слоты = бронь, доступная по правилу доступа, минус уроки репетитора, минус уроки самого ученика (у всех репетиторов). Пересечения исключаются, отменённые уроки время не занимают.
3. Запись квантуется шагом из конфигурации (по умолчанию 60 мин) и должна соблюдать дедлайн записи (`booking_lead_time_hours`).
4. Запись создаёт урок (или запись на групповой урок) + участие со снапшотом цены; репетитор получает уведомление.
5. Вступление напрямую в существующий урок разрешено только для **групповых** уроков репетитора и при соблюдении тех же условий; индивидуальная запись — через слоты.
6. Выход из урока — до дедлайна отмены (`cancellation_lead_time_hours` связи); позже — запрещено.
7. Ученик может посмотреть занятые свои слоты за период; репетитор — занятые слоты конкретного ученика (для подбора времени).

### 3.9 Оплата

1. Единица учёта — строка участия (урок × ученик), даже в групповом уроке у каждого своя сумма.
2. Сумма = длительность × замороженная цена часа (со скидкой). Отменённые участия и неявки в сумму не идут, отражаются счётчиками и «потерянной выручкой».
3. Отметка оплаты — ручной переключатель репетитора; сводка: собрано, долг, разрез по ученикам; фильтры по датам/ученику/статусу.
4. Полная оплата вперёд, частичная оплата, переплата и предоплатные пакеты **не поддержаны** — учёт бинарный (см. 4.2, идея №17).

### 3.10 Уведомления

1. Только внутренние (в приложении). Типы событий: запись на урок (`lesson_booked`), вступление (`lesson_joined`), выход (`lesson_left`), добавление (`lesson_added`), снятие (`lesson_removed`), перенос (`lesson_rescheduled`), смена статуса (`lesson_status_changed`), создание связи (`link_created`), удаление связи (`link_deleted`), смена оплаты (`payment_updated`).
2. Отправка событийная: уведомление рождается в момент действия. **Напоминания по времени (за N часов до урока) не отправляются** — настройка `notification_lead_time_hours` существует, но планировщика нет.
3. Пер-конфигурационный переключатель уведомлений есть в модели, но на поведение (отправку) фактически не влияет.

### 3.11 Статистика репетитора

1. Период: год или произвольный диапазон внутри одного года.
2. Зерно ряда — авто: день (до месяца), неделя (до ~4 месяцев), месяц (дальше).
3. Семантика: `FINISHED` — факт (урок и деньги); `SCHEDULED`/`ONGOING` — прогноз; `CANCELLED`/`NO_SHOW` — 0 ₽, но счётчики и «потерянная выручка».
4. Смысл зерна — «линия» (урок × ученик): в групповом уроке один урок и своя выручка у каждого участника.
5. Разрезы: итоги; ряд по корзинам (факт и прогноз отдельно); по ученикам (уроки, часы, выручка, прогноз, отмены, неявки, потери, первый/последний урок, статус); по дням недели; heatmap по часам; ученик × день недели; ученик × месяц; ряды учеников (спарклайны).
6. Отмены учитываются с инициатором (ученик/репетитор); ученический статус берётся из его настроек, не из эвристики.
7. Занятость: недельная норма открытых часов по броням, оценка открытых часов за период и % загрузки.
8. Прогноз: будущие уроки на 28 дней с суммами по ученикам (снапшот или оценка).
9. Отменённые участия в выручку не идут; уроки без участников не учитываются.
10. CSV-выгрузка реализована для разреза по ученикам.

### 3.12 Календарь и расписание (пользовательский интерфейс)

1. Расписание — недельная сетка: часы 07:00–22:00, ячейка 1 час, время проецируется пропорционально; текущий день подсвечен; уроки кликабельны (детали слева), репетитор видит справа форму создания, ученик — форму записи и подсветку свободных окон своих репетиторов (цвет на репетитора).
2. Фоновые брони показываются на сетке расписания приглушённо с пунктиром; черновики предпросмотра — штриховкой и без кликов.
3. Календарь — режим «месяц» (счётчик уроков в дне) и «список» (хронология со ссылками на урок); навигация месяцами, «Сегодня», переход в недельный режим.
4. Страница урока: детали, статус, тип, описание, ссылки; репетитору — участники с суммами и отметками оплаты, итог, управление составом и статусом; студенту — своё время, статус, ссылки.
5. На ключевых страницах (расписание, брони, ученики, настройки, профиль) есть туры-подсказки по кнопке `?`.
6. Роли видят своё: репетитор — ученики/брони/оплаты/статистика/настройки; ученик — репетиторы/свои настройки; админ — управление.

### 3.13 Администрирование

1. Список всех пользователей с фильтрацией по роли; просмотр и правка данных любого пользователя (имя, email, логин, персональный номер).
2. Отдельные списки: все ученики, все репетиторы, все администраторы.
3. Системные метрики: uptime, очереди, статус каналов; серверное время и UTC-офсет.
4. Журнал фронтенда: фильтры по уровню, категории, дате и тексту.

### 3.14 Время (бизнес-семантика)

1. Все проверки (создание, запись, отмена, статусы) выполняются в серверном времени; клиентское время конвертируется на границе.
2. Интервалы полуоткрытые `[start, end)`: «конец-в-конец» стык разрешён, пересечение — нет.
3. Дедлайны — это расстояние до начала урока: запись не позже чем за N часов, отмена не позже чем за N часов (настраиваются в связи).
4. Отменённые сущности время не занимают (отменённый урок, отменённое участие).

### 4.1 Как читать этот раздел

Всё здесь — **гипотезы**, а не решения. Ваши идеи не приняты как истина: каждая оценена на актуальность против цели проекта (2.2) и текущего состояния (2.5, 3). Мои идеи оценены так же честно. Статусы:

| Статус | Значение |
|---|---|
| **Реализовано** | Функциональность уже есть; если идея — про неё, смотрим доработки |

Приоритеты: **P0** — следующий этап, **P1** — ближайшие, **P2** — средний горизонт, **P3** — идеи на запас.

| 13 | Статистика: доход, время начала, посещаемость + скидки за период | Частично | Доход/часы/потери/занятость есть; нет среднего времени начала, посещаемости %, авто-скидок | P2 |
| 14 | Excel, Word, учебники | Частично | CSV есть только по ученикам; добавить экспорт платежей/расписания; учебники — часть «материалов» (№1) | P2 |
| 15 | Прогнозы нагрузки/доходов с праздниками и историей | Частично | Прогноз по расписанию на 28 дней есть; праздники/сезонность/история — нет | P2 |
| 16 | Сбор задач из разных источников | Отложено | Нужны источники задач (чат/почта/заметки) — после №7 и №18 | P3 |

### 4.3 Доработка ключевых идей (детали)

**№4 → Напоминания о занятиях (P0).** Настройка `notification_lead_time_hours` уже есть в связях; данные для напоминаний уже собираются (статистика показывает уроки на 28 дней вперёд). Не хватает одной вещи — процесса, который по времени создаёт уведомление «завтра в 15:00 урок с учеником X (цель: ...), урок: ссылка». Для «цели ученика» в напоминании нужно поле цели (см. 4.4-6). Критерий успеха: ученик и репетитор получают напоминание до начала урока в 100% будущих уроков.

**№17 → Оплата с переносом остатка (P0–P1).** Сейчас учёт бинарный: оплачено/не оплачено на строку. Кейс «внёс 2500 за урок 1500 — остаток 1000 идёт на следующий» системно не выражается. Решение — минимальная модель платежей: журнал платежей (ученик, сумма, дата, примечание, способ) + вычисляемый баланс ученика = внесено − начислено. Строка участия списывает свою сумму из баланса; если не хватает — долг, если хватает — остаток остаётся на балансе. Отметка «оплачено» превращается из ручного флага в автоматический итог списания (ручной режим оставить как переопределение). Это фундамент для №3 (остаток занятий), №20 (потребности) и №23 (планирование трат). Критерий успеха: баланс ученика сходится с реальностью, спорных «сколько он заплатил» больше нет.

**№3 → Списки учеников с прогрессом (P1).** Страница «Ученики» показывает сейчас только ставку и настройки связи. Добавить в карточку и деталь: проведено занятий (из статистики), часы, среднее в неделю, статус активности, возраст/класс (нужны поля в профиле ученика), цель занятий, остаток по пакету (если есть №17/4.4-3). «Индивидуальный наглядный план» — список тем/этапов ученика с отметками пройдено/в процессе (см. 4.4-6). Критерий успеха: по странице «Ученики» репетитор за 10 секунд отвечает «кто, что и сколько» без открыть статистику.

**№18 → Быстрые заметки (P1).** Отдельная сущность «заметка»: текст, дата, опциональная привязка к ученику/уроку, состояние «обработана/в работе». Место — закрепляемая лента на главной или отдельная страница. Дёшево (одна таблица, один сценарий, один роут, одна страница), сильно разгружает «держать в голове». Критерий успеха: ни одна тема/идея не теряется.

**№20/№21/№23 → Финансовый блок репетитора (P1–P2).** Три идеи — один модуль:
- **Потребности**: цель дохода в месяц (прожиточный минимум N ₽, опционально) → расчёт: сколько часов/уроков/учеников нужно при текущем тарифе. Поверх существующей статистики, входные данные — свои.
- **Потенциал/сценарии**: «что будет, если…» — все индивидуальные; все групповые; +N учеников; −2 часа в неделю. Учитывать праздники (календарь праздников как список дней), риски в % (средний % отмен из фактической статистики). Выход: ожидаемая выручка и требуемая нагрузка.
- **Планирование трат**: распределение выручки по статьям (аренда, налоги, материалы, подушка) и «сколько можно потратить сейчас, чтобы дожить до следующей волны оплат». Зависит от №17 (баланс).
Критерий успеха: репетитор по одному экрану отвечает «хватает ли мне текущей нагрузки и что поменять».

**№9 → Конструктор заданий/тестов (P2).** Форматы из вашей идеи — полный и правильный набор: одиночный выбор, множественный выбор, сопоставление, вставка ответов в текст/таблицу. Порядок реализации: (1) ручной конструктор + банк заданий по предмету; (2) выдача ученику и проверка; (3) автогенерация из текста/материала — уже ИИ-надстройка (№5) поверх банка. Автогенерация без банка заданий делать не стоит: качество и предсказуемость формата важнее скорости появления. Критерий успеха: репетитор создаёт тест за 5 минут, ученик решает в телефоне, результат попадает в прогресс.

**№12 + №11 → Публичность и привлечение (P2).** Публичная страница репетитора (имя, предмет, ставка, о себе, свободные окна) — мост к «сам репетитор находит учеников». Стартовый вариант привлечения — не рефералка, а **ссылка-приглашение**: ученик переходит по ссылке, регистрируется, создаёт связь (репетитор подтверждает). Реферальная программа ученика (скидка за друга) — юридически/операционно нагружена (учёт скидок за круги); отложить до появления баланса (№17), где скидки выражаются естественно. Критерий успеха: трение «сообщите репетитору номер» исчезает, связей через ссылку больше, чем по номеру.

**№5, №6 → ИИ и карты истории (P3).** Обе идеи — «слои» поверх контента, которого пока нет. Порядок: сначала материалы (№1) и задания (№9) создают данные, потом ИИ их обогащает (визуализация конспекта, презентация по тексту, генерация теста). Карты исторических событий — красивый частный случай «наглядных материалов»: делать как шаблон материала (карта + события с датами/местами), а не отдельную систему. Проверять перед разработкой: решают ли уже существующие внешние инструменты эту задачу дешевле (переносимой ссылки вместо встроенной фичи).

**№13, №15, №22 → Метрики роста (P2).** Добавить к существующей статистике: среднее время начала занятий (утро/день/вечер — распределение), посещаемость % (проведено/(проведено+отмены ученика+неявки)), доля незаполненных открытых часов (брони − уроки — свободные окна), рекомендация: «окна Ср 14:00–16:00 не заполнены 3 недели». Прогноз по нагрузке/доходам с праздниками — вход в калькулятор потенциала (№21), не отдельная фича.

**№7 → Чат (P2) и №16 → Сбор задач (P3).** Чат начинать не с мессенджера, а с «сообщений к уроку» (обсуждение конкретного занятия) — они уже снабжены контекстом и живут рядом с материалами/ссылками. Сбор задач из разных источников становится реальным только когда есть источники: заметки (№18) + чат (№7) + задания (№9) → единая лента задач репетитора.

**№10 → Статусы и каналы уведомлений (P2).** Расширить статус ученика: `ONLINE` / `OFFLINE` / `DO_NOT_DISTURB` (поверх ACTIVE/INACTIVE) и привязать к статусу политику напоминаний (за сколько часов, какой канал). Связать с №4 (планировщик) и 4.4-13 (внешние каналы).

**№14 → Экспорт и материалы (P2).** Сейчас CSV есть только в статистике учеников. Добавить экспорт: реестр оплат (CSV), расписание месяца (CSV/ICS), сводка ученика (CSV). Учебники/Word — внутри модуля материалов (№1): файл или ссылка, привязанные к уроку/ученику.

### 4.5 Технические рекомендации в поддержку идей

Указаны в порядке влияния на реализуемость раздела 4.2–4.4:

1. **Закрыть `/system/*` и `POST /logs` ролью `admin`** и добавить rate limiting на login/register — обязательное условие публичного деплоя (публичная страница №12 без этого неприемлема). Признано долгом в `docs/full-stack.md`.
2. **Фоновый планировщик** (async-цикл в процессе, поверх очередей event-infra) — под напоминания (4.4-1) и любые будущие регламентные задачи. Не требует отдельного сервиса.
3. **Модель платежей** — новые таблицы (`payments`, опционально `student_balances`) через `models.py` + авто-миграция; снапшоты цен не трогать.
4. **Индексы**: сейчас единственный индекс — `notifications.user_id`. Добавить: `lessons(tutor_id, start_time)`, `lesson_participants(student_id)`, `configurations(tutor_id)` и `(student_id)`, `bookings(tutor_id)`. Диапазонные запросы по урокам и проверки слотов — самые горячие пути.
5. **Устранить N+1** в `student_get_my_lessons` (запрос урока на каждую строку участия) — join'ом; заодно закрыть известный долг с пагинацией срезом.
6. **Хранить refresh-токен как хэш** (сейчас открытым текстом в `users.refresh_token`) — утечка таблицы не должна вести к угону сессий.
7. **Атомарность пары «урок+участие»**: одна транзакция (например, одним SQL через admin-канал/CTE) вместо create + компенсации — уберёт класс сирот.
8. **Праздники как данные**: таблица/конфиг праздничных дней — вход для прогнозов (№15) и калькулятора потенциала (№21), без внешних интеграций.

### 4.6 Методика проверки идей

Прежде чем внедрять любую идею из раздела 4, прогнать через пять шагов:

1. **Гипотеза в формате боли**: «Репетитор/ученик X сейчас делает Y руками и теряет Z» — если формулировка не складывается, идея преждевременна.
2. **Проверка без разработки**: разговор с реальными пользователями (для личного проекта — честный самоаудит: «я делаю это руками чаще раза в неделю?»).
3. **Существующий аналог**: может ли готовый внешний инструмент закрыть 80% ценности за 1% усилий (например, карты истории — внешняя карта + ссылка в материале урока).
4. **Минимальная версия**: наименьшая фича, дающая 70% ценности (напоминание — сначала в приложении, без email/Telegram).
5. **Метрика и критерий закрытия**: что считаем успехом (например, «100% уроков получают напоминание за N часов»), когда признаём идею нежизнеспособной и убираем.

Общее правило: **сначала закрыть базовый цикл «записаться → провести → оплатить → увидеть результат», потом наращивать слои** (материалы, задания, ИИ, публичность). Слои поверх дырявого базового цикла не удержат пользователей.
